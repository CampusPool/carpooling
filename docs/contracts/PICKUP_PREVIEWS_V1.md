# Private versioned pickup previews — V1

First implementation step of PICKUP_CHOICES_V1. This exposes working route/intent/preview APIs without changing any canonical trip, booking, accepted passenger or fare. Both car/bike and scheduled/on_demand labels remain supported; the existing domain factories remain the next integration boundary.

## Records and API

All endpoints require logged API user, active/unbanned account and approved current college membership. Driver writes additionally require an approved current host application and unchanged vehicle fingerprint. All reads are private/no-store. No raw invite token, location or geometry in logs/errors.

- `POST /api/mobility/pickup-plans`: `{car_id,vehicle_type,ride_mode,points:[{lat,lng},{lat,lng}]}` plus Idempotency-Key. Driver-selected endpoints are within the existing Bengaluru validation envelope. Server PathProvider creates actual vehicle path/geometry/version outside locks. Store UUID, owner/cohort/car/mode, version1, immutable path snapshot, normalized input hash, key hash, expiry30min and SHA256 of a random64hex invite token. Return raw invite only on creation; no public plan listing. Retry same input/key returns same plan without revealing invite again; changed input/key409.
- `PUT /api/mobility/pickup-plans/{id}`: same fields plus expected_version; only owner, same car/mode/ride_mode, replan outside locks then compare-and-increment revision. Rotate invite token; preserve prior preview snapshots but make their current read fail stale. No canonical route mutation.
- `POST /api/mobility/pickup-intents`: `{plan_id,invite_token,origin:{lat,lng},max_walk_meters}` plus key. Rider explicitly shares its selected origin with the plan owner; rider cannot be driver. Match plan token hash/current cohort/expiry and host eligibility. Store UUID, rider/driver/plan IDs, plan version, origin, maxwalk, intentversion1, expiry min(planexpiry,now+30min). Maxwalk is explicit integer0..10000; this is an engineering request bound, not an approved walking policy. Return no driver route geometry or token.
- `PUT /api/mobility/pickup-intents/{id}`: rider only, `{expected_version,origin,max_walk_meters}`; increment immutable input revision and bind current plan revision. New preview required.
- `GET /api/mobility/pickup-intents/{id}`: rider or exact plan owner only, current eligibility and expiry. Driver sees only the origin explicitly shared with them.
- `POST /api/mobility/pickup-intents/{id}/previews`: plan owner only; `{expected_plan_version,expected_intent_version,max_detour_meters,max_detour_seconds}` plus key. Explicit integer detour preferences0..100000m/86400s are bounded engineering inputs, not pricing or operating policy. Check current plan/intent version, host/member/car/input graph configuration before I/O. Invoke planner, then atomically recheck exact versions/eligibility before storing UUID, immutable snapshot, request/key hash and expiry min(now+5min,planexpiry,intentexpiry). Same-key same-input retry converges; changed input409. No partial/stale graph result becomes current.
- `GET /api/mobility/pickup-previews/{id}`: only exact driver/rider, eligibility/current plan+intent versions and expiry. An outdated revision409; expired410. Always `booking_enabled:false` in this slice; UI must not present preview as an assigned ride.

Shared service uses `PickupPreviewPlanner::preview(array $driverPath,array $origin,string $mode,int $maxWalk,int $maxDetourM,int $maxDetourS):array`. driverPath is the stored PathProvider output plus `points` (two requested endpoints). Planner output has `direct`, `meeting`, evaluated candidate count, provenance and limits. Direct road path goes start->rider->destination, showing actual snapped pickup and signed/added detour, never assuming zero walking from an off-road origin. Meeting candidates come from bounded projections/vertices along the forward geometry; rank eligible candidates by actual shortest-distance pedestrian path, then driver detour and deterministic position tie-break. At most4 candidates and a bounded overall I/O deadline; describe best among evaluated candidates, not globally shortest. Include separate pedestrian and vehicle snapped locations/handoff gap. Route/snap/access evidence is not a safety certification. Foot outage/no route leaves meeting unavailable; no motorized walking fallback. Wrong or mixed graph identity fails closed. Planner/service throw `PickupException` with safe machine code/httpStatus; provider RoutingException remains translated safely.

## Atomicity and authority

No external I/O inside publication/revision trust locks. On commit lock affected user rows in sorted order, current membership/host/vehicle, plan then intent then preview retry row; recheck versions and timestamps. Do not trust posted metrics/geometry/identity/revisions other than expected-version comparison. No DB effect on canonical ride/payment/support tables. Keep invite hash out of API projections. Missing production graph config fails closed; testing fake providers remain explicitly injected in tests.

Required tests: ownership/cohort/private token errors; input/hash idempotency; graph mismatch/no path; direct and meeting metrics; network work outside commit locks; changed driver/rider revision during I/O; revoked membership/host/car; concurrent same-key preview; stale/expired reads; no trip/booking/fare writes. Actual local three-graph MySQL/API proof supplements mocked failure cases. Browser/device/canonical assignment remain separate gates.

Creation and preview retry convergence is limited to current, eligible, unexpired records. A reused key never revives an expired proposal or reveals an invite token again; expired creation retries return410 and retain the original record. Update operations preserve the original creation request hash. Per-provider timeout is capped by the remaining20second planner budget; the planner checks the deadline after each call. Strict graph identity is also required on private read/replay.
