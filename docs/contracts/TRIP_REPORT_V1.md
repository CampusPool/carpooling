# TRIP_REPORT_V1

20 October2026. S7 trip-linked reporting reuses upstream SupportTicket/Reply and audited operator workflows. Reporting never changes trip execution, bookings, dispatch or financial state. No emergency-response or phone-notification guarantee.

`POST /api/mobility/trips/{trip}/reports`, numeric canonical trip, existing logged/active middleware. Required printable ASCII Idempotency-Key1..100bytes. JSON subject3..160chars, message_markdown1..4000chars with upstream SupportTicketMessage user-content rule. Reject attachments and client authority fields by ignoring unknown input; no uploads in this increment. Invalid422, unrelated403 TRIP_REPORT_FORBIDDEN, changed payload/key409 IDEMPOTENCY_CONFLICT. A participant endpoint has no unconditional admin bypass: owner or exact actor's Passenger accepted/waiting-payment/canceled recovery row only. Unknown trip404.

Normalize subject before validating length; rider rows must be TYPE_PASAJERO. Request throttling retains the upstream configured support-create allowance (default5/hour) in a dedicated report scope, using explicit API JWT identity and the existing database cache for atomic increments. Laravel may sort throttle before custom logged middleware, so default-user-only lookup would incorrectly share the anonymous IP bucket. File-cache increments also lost a count in actual concurrent probing. The dedicated DB limiter leaves global cache and existing rate buckets intact. Retries/conflicts consume attempts;429 means wait for Retry-After, never rotate accounts/keys to bypass it. This is request-abuse control, not ride/case authority or a transactional global capacity guarantee.

Atomic lock order Trip -> actor/trip/key metadata -> newly created SupportTicket/Reply. Metadata mobility_trip_report_requests unique(trip_id,actor_id,idempotency_key), fingerprint SHA256 validated subject/message, canonical ticket_id, timestamps. FK widths match upstream unsignedInteger IDs, ticket restrict-delete. The canonical trip lock serializes concurrent same-trip creations before absent-key check; uniqueness is an additional database guard. No lifetime content deduplication: different keys allow separate incidents with identical text. Same key/payload returns the same canonical ticket ID with its current safe fields,200 for first/replay. No report-body duplication in metadata.

Create upstream ticket user_id/created_by authenticated reporter, trip_id exact trip, type report, source web_form, priority high, status Open, admin unread1/user unread0, last_reply_at now. Create one initial non-admin reply with authenticated actor. Reuse SupportTicketService::appendOpeningAutoReply inside transaction for local ticket/reply state only. If added, notify reporter with existing SupportTicketReplyNotification after commit and outside all trip locks; replay sends no second notification. Notification failure emits a sanitized event and does not roll back a committed report. No persistent-delivery claim from this best-effort local notification; real push, failure recovery and staffed response remain open.

Response data only id,trip_id,subject,status,type,priority,created_at,updated_at. Do not return internal notes, assignment metadata, reporter contact, other participants, raw models or transport secrets. Existing user support-ticket list/detail/reply APIs must also hide internal_note_markdown (currently raw upstream model serialization would expose it). Coordinator integration patch sanitizes those user responses; administrator case detail retains the note and permissioned access. Test all user response variants and replay after operator adds a private note.

Existing `/api/support/tickets` owner views/replies and `/api/admin/support/tickets` queue/assign/reply/needs-review/resolve remain canonical. Admin APIs retain `can:admin.support.tickets`; helpdesk/superadmin roles currently have it. User::resolvedAdminRole defaults legacy null/unrecognized admin_role to superadmin: do not claim plain is_admin alone is denied under existing behavior. No auth enhancement is authorized in this slice. Do not bypass middleware in acceptance tests. Existing audit logger records actual admin mutations, never impersonate an operator for participant submission.

Client adds trip-report form/recovery with stable key on uncertain retries, explicit new-report reset, safe plain-text messages and scoped existing case viewing/reply. Operators use existing case APIs with real permission handling and audit, not financial controls. Hidden UI is no authorization. Discard in-flight responses after account change/logout. Existing trip chat stays separate.

Acceptance: anonymous/inactive/unrelated/admin-outsider/malformed denial; owner/accepted/waiting/canceled report; exact trip/actor identity; same-key sequential/concurrent convergence, changed conflict, different-key identical-text distinct cases; atomic ticket/reply/metadata rollback on fault; reporter ticket privacy including internal notes across list/detail/create replay/reply; existing operator queue and audited assignment/reply/needs-review/resolve; local notification state without repeated replay delivery; hashes prove trip/booking/dispatch/money unchanged. Isolated MySQL suites and actual localhostJWT/concurrent HTTP required; browser/phone acceptance separately labeled.
