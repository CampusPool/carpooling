# Recurring programs and dated inventory v1

20 October 2026. Original product policy for S3; no recovered Hopr server rule is implied. Keep both full ride modes in scope; authentication enhancements remain deferred. Source contract: ROUTE_QUOTES_V1.md. This contract is an implementation target, not availability evidence.

## Behavior and authority

A program is a versioned host intent, not a booking. Every materialized service date has its own canonical Trip, points/routes, immutable per-date quote/publication, Passenger rows, seats and lifecycle. Unique(program_id,service_date) and unique trip_id prevent duplicates. Published occurrences are never silently rewritten, deleted or regenerated, including cancelled dates. Calendar processing advances generated_through across processed dates, including excluded weekdays/skips; repeated generation only considers later dates. All dates/time are Asia/Kolkata; quote expiry is UTC.

Programs span date_from today..today+21 days, date_to >=date_from and <=date_from+365 days. Mask Monday=1..Sunday=64,1..127; time HH:mm; car1..5 passenger seats/bike exactly1. Initial generation processes through min(date_to,max(today+14,date_from+7)), capped today+28. Publication uses S2 >now+15min and <=now+30days; past/too-near dates are skipped, never backfilled implicitly. Later generation is bounded through <=today+28, at most29 calendar dates/run. No external call runs while program/seat/admission locks are held.

Creation consumes the fresh owner quote for the first eligible occurrence. Each other occurrence receives a new server-created child quote with immutable same trusted metrics/fare/points/profile and provenance parent_quote_id, then calls existing OfferService under the enclosing transaction. Later generation first obtains a fresh RouteQuoteService quote for the program's server-owned pickup IDs/mode outside the generation transaction, then rechecks actor/program version. It must match the currently accepted pricing_version and not exceed max_fare_minor; otherwise return409 PROGRAM_REQUOTE_REQUIRED and preserve inventory. Provider failures do not advance generated_through or consume an action key. The unused preparation quote may expire after a competing generation wins; no orphan trip is allowed. No raw client snapshot/geometry/fare becomes authoritative.

Pause means: no new generation, discovery, requests or acceptances (including autoaccept) for program occurrences. Already accepted journeys and authenticated cancellation/lifecycle/payment recovery remain available. Resume reopens still-planned published dates; it does not recreate cancelled/skipped dates. Existing pending requests are retained but cannot be accepted while paused. UI must disclose this behavior. Scope is active/paused; ending date and pause stop repetition without erasing rides.

Edits change only not-yet-published future dates. Every edit takes effect exactly generated_through+1 (or date_from before generation). Existing occurrence IDs, times, fares, capacities and bookings stay fixed. Mask/time/seats/end date can change; date_to cannot precede generated_through. No implicit rescheduling of published inventory: explicitly skip that date and make a separate replacement offer if needed. A fresh unconsumed root owner quote for the same pickup/drop-off IDs/mode may explicitly refresh the future pricing version/cap; record it as approval evidence, not another seat reservation. All such decisions are versioned/audited, including approval_quote_id and the persisted quote snapshot SHA256 in the action after_snapshot. Published-date replacement/edit automation is not claimed.

Skip a future date explicitly and irreversibly for this program. If unmaterialized, persist an exception so generation omits it. If materialized, only planned canonical lifecycle can cancel; delegate MobilityController::transition(cancel) and retain bookings/history. Create PaymentService::blockRefundOrDispute(reason=recurring_occurrence_cancelled) for every affected pending/accepted/waiting-payment booking so late capture/release cannot silently escape recovery. This records recovery work, not a refund or payout. Return whether existing payment attempts require operator financial recovery. A started/completed occurrence cannot be skipped. Never treat program pause as cancelling accepted rides.

## APIs and errors

All use existing authenticated logged middleware. New activity/create/generate/edit requires active unbanned approved member and exact current owned complete approved vehicle, fingerprint/mode/college rechecked under locks. Owner-only pause/skip/read recovery is retained for suspended members; no cross-owner program access (404). No self-granted roles or new auth work. Missing India runtime/college configuration503. Errors are `{"error":{"code":"CODE"}}`, never SQL/provider internals.

All mutations require visible-ASCII Idempotency-Key8..100. Owner+create-key and program+actor+action-key store request hash and exact committed response. Same key+payload returns committed result, changed payload409. Control mutations require expected_version positiveint; stale409. Validate scalar types/unknown fields/dates without500.

- POST `/api/mobility/recurring-programs`: quote_id,car_id,weekly_schedule,departure_time,date_from,date_to,total_seats,optional description<=600. Response201 `{data:{program:<summary>,occurrences:[<dated item>],existing:false}}`; replay200 existingtrue with original IDs. Rate bounds max10 active/paused programs/owner and3 creations/rolling24h; return429 without banning. Normal canonical creation-limit count excludes already-linked recurrence Trip IDs; ordinary single-trip anti-abuse otherwise unchanged.
- GET `/api/mobility/recurring-programs`: owner-only list page_size1..50 default20, after UUID optional stable lexicalid cursor; `{data:[summaries],next_cursor}`. Summary includes id,version,state,car_id,vehicle_type,from_name,to_name,pickup_point_id,dropoff_point_id,weekly_schedule,departure_time,date_from,date_to,total_seats,max_fare_minor,pricing_version,generated_through,next_edit_from,synthetic_only,last_generation_code. No provider credentials/review notes.
- GET `/api/mobility/recurring-programs/{program}`: owner-only summary and occurrences (page_size1..50 default30,after_date optional YYYY-MM-DD), exceptions; `{data:{program:<summary>,occurrences:[...],exceptions:[...],next_cursor}}`. Occurrence item service_date,trip_id,program_version,departure_local,seats_available,total_seats,seat_price_minor,lifecycle_state; canonical data supplies these fields. Bounded exceptions response with same date window; no unbounded history dump.
- POST `/api/mobility/recurring-programs/{program}/generate`: expected_version,until (YYYY-MM-DD<=today+28). No-op/idempotent for already processed range; fresh provider only if new eligible dates. Response200 data program summary + generated occurrences (existing item IDs for replay). Row-unique generation must remain correct for two simultaneous runs with distinct keys.
- POST `/api/mobility/recurring-programs/{program}/control`: expected_version,action pause/resume,reason string1..500. Increment version only on actual state change; invalid same-state409; audit before/after/reason/actor.
- POST `/api/mobility/recurring-programs/{program}/edit`: expected_version,effective_from exactly next_edit_from,optional weekly_schedule/departure_time/total_seats/date_to/quote_id,reason1..500. At least one change; fresh quote optional only for future pricing refresh with same catalog route/mode. Existing published occurrences unchanged. Increment version/audit.
- POST `/api/mobility/recurring-programs/{program}/exceptions`: expected_version,service_date,action=skip,reason1..500. Date in program range and >=today, must not be a past departure. Increment version/audit; exact key replay no duplicate cancellation or payment blocks. Response program summary, skipped service_date,trip_id nullable,financial_recovery_required boolean.

## Locks and integration

Generation: lock owner User -> membership -> owned Car -> exact host approval -> program -> quote/catalog as OfferService requires. Create child quotes and canonical trips/occurrence links within one outer transaction; quote use+program/through/audit commit together. Never lock existing trip rows during generation. External routing and pricing refresh validation before these locks; recheck version/source after provider returns. Separate program generation rate bound prevents treating a large legal recurrence as abuse.

Controls/admission must coexist with existing trip-first lifecycle/payment locks. Control reads target program/trip IDs without locks first, then inside transaction locks owner User (controls only), all relevant existing canonical Trip rows sortedID -> lifecycle/participant rows as needed -> program -> exception/action rows. Recheck version/owner/target mapping after locks. Admission middleware for new request/accept locks Trip then program through `$next`, denies paused/skip; autoaccept executes under the same transaction. Never introduce program->existingTrip lock inversion. Generation holds program only while inserting NEW trips, never existing ones. Keep recovery/cancel/start/board/alight/complete/payment routes accessible under their existing participant rules.

Discovery (new API and legacy cohort search) excludes program occurrences whose program is paused or whose date is skipped. Canonical per-date cancellation is never automatically undone by generator. Worker only stages independent code; coordinator verifies combined migrations/patch replay/tests and actual HTTP generation/admission. Scheduler command `mobility:generate-recurring --limit=20` does bounded active-program work; register with Laravel scheduler only when explicit MOBILITY_RECURRENCE_SCHEDULER_ENABLED=true (defaultfalse), daily India time. Local CLI can be exercised; no public hosting/paid service is authorized.
