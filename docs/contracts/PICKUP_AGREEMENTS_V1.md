# Exact pickup agreements — V1

Implements the selection/consent part of PICKUP_CHOICES_V1 and PICKUP_PREVIEWS_V1. A pickup agreement records where the two people agree to meet. It does **not** reserve a seat, fix a fare, assign a driver, publish a departure or create a ride. Every response includes `booking_enabled:false` and `scope:pickup_only`. The UI must say “Pickup agreed; ride not booked.” Both car/bike and scheduled/on_demand plan labels are preserved; canonical mode execution is a separate integration gate.

## Boundary with canonical booking

Current intents have origin only. Before any future booking writer can consume an agreement it must bind the rider's destination, actual occupied interval, current immutable quote/fare, scheduled departure or dispatch request and exclusive capacity/assignment. Driver approach/detour metrics in this preview are not the rider's chargeable journey. A changed destination can change the driver detour and requires fresh terms and consent. Existing accepted passengers and recurring occurrences retain their original immutable terms. Do not create dynamic precise origins in the globally searched nodes_geo table or relabel them as publicly verified catalog stops. The dynamic endpoint authority/privacy contract must precede that integration. This increment intentionally adds no quote, catalog, Trip, Passenger, dispatch, fare or payment writes.

## Records

`mobility_pickup_selections` has immutable UUID, plan/intent/preview identities and revisions, exact driver/rider/car/cohort/mode identities, per-intent sequence `version`, choice, preview SHA256, immutable `terms` JSON and SHA256, create key/request hashes, expiry, driver selection time. Mutable state is only pending/confirmed/declined/revoked/superseded, rider confirmation and closure times. A unique nullable `active_intent_id` enforces one current selection per intent, and `(intent_id,version)` is unique. The intent row serializes sequence allocation. Old records remain historical; a new selection explicitly supersedes the preceding active pickup-only agreement and needs fresh rider confirmation. Nothing transfers old consent to new terms.

Terms schema `pickup-agreement-v1` includes exact plan/intent/preview IDs and revisions, participants, car/vehicle fingerprint, college, vehicle/ride mode, original rider origin, driver requested endpoints, preview graph versions/limits, selected option copied in full from the stored preview, and `access_verified:false`. Store the hash of the **raw** stored preview JSON and exact serialized terms. A client may post an enum, never coordinates/metrics/fare. Direct and meeting choices map exclusively to stored `direct` and `meeting`; require available=true, matching choice enum, structured selected vehicle path/pickup/detour and exact graph identity. Meeting additionally requires a structured pedestrian path/point/distance/gaps with the preview's exact foot graph. Malformed stored options fail closed. Null foot graph is allowed only for direct when meeting was unavailable. Routing/snaps and people's acknowledgment do not establish safe/legal access; acknowledgment leaves access_verified false.

`mobility_pickup_selection_actions` records selection ID, actor, action confirm/decline/revoke, key hash, request hash, timestamps. Unique `(actor_id,key_hash)` prevents a key being repurposed for another transition/selection. Replays never reverse a later state. No raw keys or private coordinates in logs/errors.

## API

All endpoints use existing authenticated/logged API middleware and private/no-store responses. Fresh active membership and exact approved host/car fingerprint required. Outsiders cannot read or act. Fresh graph, plan/intent revisions and expiry are required for selecting/confirming and current reads.

- `POST /api/mobility/pickup-previews/{id}/selections`, driver only. Exact body `{choice,expected_plan_version,expected_intent_version}` and Idempotency-Key. Choice `DIRECT_RIDER_PICKUP` or `ON_ROUTE_MEETING_POINT`. Validate preview through existing service; select only its available stored alternative. Expiry min(now+5min, preview, intent, plan). Same driver/key and original body returns original selection if still current, eligible, unexpired and active; changed body409. Replaying a superseded record must not replace the current selection. A new key creates a new sequence and supersedes the old selection atomically.
- `GET /api/mobility/pickup-selections/{id}`, exact rider or driver only. Fresh eligibility, plan/intent/graph/expiry required, hash/linkage revalidated. Closed selections can be read while current inputs remain valid; `actionable` true only for active pending selection. Return `selection` with ID, version, state, choice, terms/hash, IDs/revisions, expiry, confirmation/closure times, scope/booking flags. Never expose key hashes/request hashes/invite token.
- `POST /api/mobility/pickup-selections/{id}/confirm`, rider only. Exact `{expected_version,terms_hash,access_acknowledged:true}` and Idempotency-Key. Compare exact sequence and hash; require active pending row, current source revisions, graph, eligibility and unexpired proposal. Driver selection constitutes driver consent to these pickup terms; rider confirmation records rider consent to the same immutable bytes. Confirmed retry converges without changing timestamps; closed/stale/expired proposals cannot revive. `confirmed` is pickup agreement only.
- `POST /api/mobility/pickup-selections/{id}/decline`, rider only; exact `{expected_version,terms_hash}`, key. Pending only. Clears active slot and sets closed time. Confirmed row requires revoke, never silently becomes declined.
- `POST /api/mobility/pickup-selections/{id}/revoke`, either participant; exact `{expected_version,terms_hash}`, key. Pending/confirmed only; clears active slot and sets closed time. Revoke/decline may close an expired/stale proposal without requiring old graph availability, but still require fresh participant eligibility, immutable identities/hash and exact version. Historical reads continue to follow current source policy. Cancellation cannot edit terms or touch a canonical ride.

Errors use existing PickupException:403wrongactor/eligibility,404missing,422strictinput/unavailable choice/malformed option,409revision/hash/key/closed/conflict/graph,410expiry. Never return private terms in errors. Reconnect GET and reusing original in-memory keys are supported; no local location/token persistence.

## Atomicity and verification

No provider I/O in selection/consent transactions. Deterministic locks: sorted users → sorted memberships → car → host applications → plan → intent → preview → existing selection rows ordered ID → action retry row. Preflight identities are immutable and rechecked after locking; do not establish a repeatable-read snapshot before trust locks. All input updates already lock users/plan/intent. Locking a common participant serializes cross-selection actor/key races. Lock intent before computing max sequence; release prior active slot before inserting next selection. Verify exact source linkage and current graph pins after locks. Store current vehicle fingerprint and reject any later mismatch.

Required DB tests cover both choices/modes/vehicles, wrong actor, strict fields/client metric injection, hash/version mismatch, source tamper, changed graph/revision/host/membership, expiry, unavailable or malformed choice, supersession, confirmation/decline/revoke races, retry key conflicts, rollback and no canonical/money writes. Actual graph API proof must confirm exact stored geometry/hash roundtrip. Client must show two driver choices, exact rider review, separate unmapped gaps, pending/confirmed/closed and friendly refresh failures. Static checks do not establish browser/device usability; actual TCP JWT/concurrency, browser and device gates must be recorded separately.
